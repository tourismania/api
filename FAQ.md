# FAQ


## 1. Зачем в `internal/infrastructure/persistence/postgres/db/users.sql.go` передается ctx?


`ctx` здесь выполняет сразу несколько важных функций:

**1. Отмена запроса (Cancellation)**
Если HTTP-обработчик завершился раньше (клиент закрыл соединение, timeout сработал), контекст отменяется — и `QueryRow(ctx, ...)` прервёт запрос к базе ещё до того, как PostgreSQL вернёт результат. Без `ctx` запрос бы продолжал выполняться вхолостую.

**2. Таймауты**
Если где-то выше по стеку сделали `context.WithTimeout(ctx, 5*time.Second)`, этот дедлайн автоматически распространяется на запрос к БД. Не нужно отдельно настраивать таймаут на уровне SQL.

**3. Трассировка и телеметрия**
Библиотеки вроде OpenTelemetry или pgx-instrumentation умеют вытаскивать из контекста span/trace ID и добавлять SQL-запрос как дочерний span. Это даёт видимость: сколько времени именно этот запрос занял внутри конкретного HTTP-запроса.

**4. Передача значений (request-scoped data)**
В контекст можно положить, например, user ID аутентифицированного пользователя или request ID — и middleware для логирования/аудита может их оттуда достать.

**Коротко:** `ctx` — это не просто формальность. Это механизм, который связывает жизненный цикл SQL-запроса с жизненным циклом HTTP-запроса, давая возможность вовремя отменить, ограничить по времени и проинструментировать обращение к БД.


## 2. Деньги и валюты: почему цена хранится целым числом, а не float? Почему справочник валют в коде и без `CHECK` в БД?

Вопросы из ревью SDD-изменения `add-flight-price-currency` (цена перелёта, issue №26).

**Почему не float.** `float64` (и `number` в JSON/JS) — двоичная дробь: `0.1`, `0.10`, `19.99` в нём представляются приближённо. Для денег это значит:
- ошибки сложения: `0.1 + 0.2 = 0.30000000000000004` — итог оффера и будущий пересчёт валют копят погрешность;
- ненадёжное сравнение: правило «тот же набор перелётов» и обновление «только цены» сравнивают суммы, а `==` на float ломается;
- потерю точности на больших суммах: выше 2^53 не все целые представимы.

**Почему целое число минорных единиц.** Сумма хранится в копейках/центах/филсах валюты (`price_minor BIGINT`), на проводе — десятичной строкой (`"12345.50"`). Сложение и сравнение точные, `"100"` и `"100.00"` дают одно значение. Это стандартный приём (ISO 4217, Stripe, Adyen).

**А если у валюты 3 знака после точки (KWD, TND) или 0 (JPY)?** Масштаб не зашит: у каждой валюты в справочнике есть `Exponent` — число знаков по ISO 4217. `"12.345"` KWD → `12345`, `"500"` JPY → `500`. Схема БД и контракт от этого не меняются. Предел — 10 цифр целой части, при 3 знаках это ~10^13, а `int64` держит ~9,2·10^18.

**Почему не `NUMERIC` + decimal-тип.** Тоже точно, но число знаков всё равно пришлось бы проверять по валюте, а через маппер и домен потянулся бы `pgtype.Numeric` или новая зависимость. Минорные единицы дают то же самое проще.

**Почему справочник валют в коде, а не в БД.** Это системные данные (ISO 4217 меняется раз в годы), они нужны при валидации без запроса к БД, а изменение проходит обычный code review и релиз. Справочник — `internal/domain/money/currency.go`, порядок изменений — `docs/currencies.md`.

**Почему в БД нет `CHECK` на валюту и сумму.** `CHECK (currency IN (...))` продублировал бы справочник: каждая новая валюта требовала бы миграции, а при рассинхроне кода и БД клиент получал бы `500` вместо понятного `400`. Записать цену можно только через api, инварианты проверяет домен.


## 3. Почему цена и валюта проверяются в application-слое, а не валидатором presentation или в `config/`?

Вопрос из ревью api PR №27.

Валидатор presentation проверяет **форму** запроса: поле есть, тип верный, длина и формат в пределах контракта. Есть ли валюта в справочнике и сколько у неё знаков после точки — **бизнес-правило**: его знает домен (`internal/domain/money`). Если зарегистрировать такую проверку в валидаторе через `config/`, правило будет проверяться дважды (на границе и в домене), а composition root начнёт передавать доменную логику в presentation — он должен только собирать зависимости.

Поэтому presentation проверяет только обязательность `price`/`currency`, а `helpers.BuildFlights` в application-слое разбирает цену через `money.Parse` и возвращает `apperror.FieldError` с полем (`Price`/`Currency`) и правилом (`money`/`currency`). Presentation отдаёт его в `meta` ответа `400 validation failed` в том же виде, что и ошибки валидатора, — для клиента контракт не изменился. Правило зафиксировано в `CLAUDE.md` («Валидация по слоям»).
