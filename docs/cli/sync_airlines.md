# CLI-команда `airlines sync`

> **Файлы:** [handler.go](../../internal/application/command/sync_airlines/handler.go), [parse.go](../../internal/application/command/sync_airlines/parse.go), [events.go](../../internal/application/command/sync_airlines/events.go), [wikidata/airlines.go](../../internal/infrastructure/geo/wikidata/airlines.go), [static/countries_ru.go](../../internal/infrastructure/geo/static/countries_ru.go), [cli/airlines.go](../../internal/presentation/cli/airlines.go)
>
> **Требования:** sdd `openspec/changes/add-flight-segment-airline` (после архивации — `openspec/specs/travel-services/airlines/spec.md`).

Команда наполняет справочник авиакомпаний `airlines` (и общую со справочником аэропортов таблицу
`countries`) из Wikidata. Запускается вручную раз в месяц администратором (см. `README.md → CLI`).
HTTP-эндпоинта синхронизации нет, справочник через HTTP не редактируется.

```bash
go run ./cmd/cli airlines sync --dry-run   # запросы, разбор и журнал аномалий без записи в БД
go run ./cmd/cli airlines sync             # полная синхронизация
```

Вывод разделён: строки прогресса и итог — в **stdout**, журнал аномалий — JSON-строками в **stderr**.

---

## 1. Источник и запрос

Источник — только Wikidata (публичный SPARQL-эндпоинт `query.wikidata.org`). Берутся все элементы с
кодом ICAO авиакомпании (`P230`) — и действующие, и прекратившие работу. Фильтра «экземпляр класса
авиакомпания» нет: `P230` есть практически только у авиакомпаний, а обход иерархии классов на
публичном WDQS приводит к таймаутам.

```sparql
SELECT ?item ?icao ?iata ?nameEn ?nameRu ?iso2 ?dissolved ?precision WHERE {
  ?item wdt:P230 ?icao .
  OPTIONAL { ?item wdt:P229 ?iata . }
  OPTIONAL { ?item rdfs:label ?nameEn . FILTER(LANG(?nameEn) = "en") }
  OPTIONAL { ?item rdfs:label ?nameRu . FILTER(LANG(?nameRu) = "ru") }
  OPTIONAL { ?item wdt:P17 ?country . ?country wdt:P297 ?iso2 . }
  OPTIONAL {
    ?item p:P576 ?dissolvedStatement .
    ?dissolvedStatement a wikibase:BestRank ;
                        psv:P576 ?dissolvedValue .
    ?dissolvedValue wikibase:timeValue ?dissolved ;
                    wikibase:timePrecision ?precision .
  }
}
ORDER BY ?item ?icao ?iata ?nameEn ?nameRu ?iso2 ?dissolved
LIMIT 10000 OFFSET …
```

- Ответ — по строке на сочетание значений (элемент с двумя кодами IATA даёт две строки); сортировка
  по всем переменным делает постраничную выдачу `LIMIT/OFFSET` устойчивой. Следующая страница
  запрашивается, пока страница полная.
- `wdt:` и `wikibase:BestRank` — только значения лучшего ранга.
- **Точность даты** `P576`: до дня — как есть; до месяца — 1-е число; до года и грубее — 1 января.
  Даты до нашей эры и неразборчивые значения отбрасываются.
- Повторы — общий механизм клиента Wikidata: 5xx, 429 и сетевые ошибки повторяются, всего 4 попытки
  с паузами 3, 6, 12 с; другие ответы и исчерпание попыток — ошибка, ненулевой код выхода.

Что ещё есть в источнике и **не** загружается (добавить — `OPTIONAL` и столбец): дата основания
(`P571`), штаб-квартира (`P159`), хабы (`P113`), альянс (`P114`), материнская компания (`P749`),
позывной (`P432`), сайт (`P856`), логотип (`P154`).

## 2. Правила разбора

Строки группируются по QID элемента (`source_id`), затем для каждой авиакомпании:

| Поле | Правило |
|---|---|
| `icao` | Коды ровно из 3 заглавных латинских букв; другие отбрасываются. Нет ни одного корректного — авиакомпания **пропускается** (`icao_invalid`). Несколько корректных — сохраняется первый по алфавиту (`icao_multiple`). |
| `iata_codes` | Все коды из 2 заглавных латинских букв или цифр; другие отбрасываются. Наружу api их не отдаёт. |
| `name` | Английская метка. Нет — авиакомпания **пропускается** (`name_en_missing`). |
| `name_ru` | Русская метка, **только если страна — ровно одна и это `RU`**; иначе `""`. |
| `country_iso2` | Единственная страна. Нет или несколько (`country_multiple`) — `NULL`. |
| `dissolved_on` | Самая поздняя из дат прекращения деятельности; нет — `NULL` (действует). |

Название страны в `countries` — из встроенного русского списка (`static/countries_ru.go`), для
неизвестного кода — сам код. Upsert страны по `iso2` перезаписывает название.

## 3. Запись

1. `ListSourceIDs` — записи справочника из источника по `source_id`. Если у одного `source_id`
   несколько записей — **ошибка до записи** (ручной разбор; уникального индекса нет намеренно, см.
   миграцию `021`).
2. **Проверка полноты.** Не пришло больше **10%** видимых в поиске записей справочника (без уже
   скрытых дублей и пропавших) — **ошибка до записи**, ничего не скрывается: обрыв ответа WDQS
   иначе выглядел бы как массовая пропажа авиакомпаний. Перезапустите синхронизацию.
3. Страны → авиакомпании: известный `source_id` — `UPDATE` по `id` (id сохраняется), новый —
   `INSERT`. Ошибка записи останавливает прогон с `source_id` и названием авиакомпании; запись не
   транзакционна — записанное до ошибки остаётся.
4. Вернувшиеся из источника пропавшие — пометка снимается (снова видны в поиске под прежним id).
5. **Не пришедшие записи** (кроме уже слитых): запрос перенаправлений
   `VALUES ?old { wd:Q… } ?old owl:sameAs ?new` пачками по 200 QID.
   - Перенаправлен на элемент записи справочника — запись становится **дублем** этой записи
     (`merged_into_id`; уже слитые в неё — тоже переводятся, цепочка не растёт), событие `merged`.
   - Перенаправлен на элемент, которого нет в справочнике, — **пропавшая** (`missing_since`),
     событие `merge_target_unknown`.
   - Не перенаправлен — **пропавшая**, событие `missing`.
   - Уже пропавшая и по-прежнему пропавшая — без повторной пометки и события.

Дубли и пропавшие не удаляются и не находятся поиском (`GET /api/v1/airlines`), но остаются для
сегментов, которые на них уже ссылаются (`GET /api/v1/airlines/{id}` их отдаёт).
**Сегменты перелётов синхронизация не меняет никогда.** Слитая запись не «расслаивается» — отмену
слияния в Wikidata разбирают вручную. Служебная запись «Неизвестная» (`id = 1`, без `source_id`)
синхронизацией не создаётся, не меняется и не скрывается.

Итог в stdout:

```
anomaly airline_sync.<event>=<N>         # по строке на каждый вид, если были
Done. Synced <N> countries, <N> airlines (<N> dissolved), <N> skipped, <N> anomalies.
[dry-run] countries=<N>  airlines=<N>  dissolved=<N>  skipped=<N>  anomalies=<N>   # вместо Done в --dry-run
```

`--dry-run` выполняет все запросы к источнику и чтения справочника, разбор и журнал аномалий
(включая дубли и пропавшие), но ничего не пишет.

## 5. Мониторинг

Каждая неоднозначность источника — отдельное предупреждение `WARN` в stderr в формате JSON
(`log/slog`, JSON-handler). Аномалии **не** меняют код выхода. Сбора логов и алертов в проекте пока
нет — это строка бэклога sdd («Алерты по аномалиям синхронизаций справочников»); журнал уже
пригоден для фильтра и алерта.

Общие атрибуты каждого события: `event`, `source_id` (QID), `icao`, `name` (английское; пустые, если
нет). **Имена событий — стабильный контракт**: переименование — ломающее изменение для фильтров и
алертов.

| Событие | Когда возникает | Доп. атрибуты | Что делать администратору |
|---|---|---|---|
| `airline_sync.icao_shared` | Один код ICAO у нескольких **действующих** авиакомпаний | `source_ids`, `names` | Обе записаны и видны в поиске. Если это дубль одного элемента — слить элементы в Wikidata, следующий прогон скроет дубль. Если разные (бренд и юрлицо, лаг отметки о закрытии) — ничего. |
| `airline_sync.icao_multiple` | Несколько корректных кодов ICAO у элемента | `codes`, `kept` | Обычно старый и новый код — проставить в Wikidata ранг/дату окончания у старого. |
| `airline_sync.iata_multiple` | Несколько кодов IATA у элемента | `codes` | Сохраняются все; поправить в Wikidata, если это ошибка. |
| `airline_sync.name_en_missing` | Нет английской метки — **пропущена** | — | Добавить английскую метку элементу в Wikidata. |
| `airline_sync.icao_invalid` | Нет ни одного корректного ICAO — **пропущена** | `codes` (некорректные) | Исправить код в Wikidata (3 заглавные латинские буквы). |
| `airline_sync.country_multiple` | Несколько стран — страна не заполнена | `countries` | Оставить одну страну (`P17`) лучшего ранга в Wikidata. |
| `airline_sync.merged` | Запись стала дублем: источник слил её элемент | `merged_into_source_id` | Ничего: запись скрыта из поиска, старые офферы верны. Если слияние ошибочно — разбор вручную. |
| `airline_sync.missing` | Запись пропала из источника без слияния | — | Проверить элемент в Wikidata (удалён, стёрт код ICAO). Вернётся — снова станет видна. |
| `airline_sync.merge_target_unknown` | Элемент перенаправлен на элемент без записи в справочнике (у цели нет `P230`, нет английской метки и т. п.) | `merged_into_source_id` | Запись скрыта как пропавшая. Добавить цели недостающие данные в Wikidata — следующий прогон сольёт. |

Где искать журнал: stderr команды. Локально — терминал; в docker —
`docker compose exec tourismania_app /app/cli airlines sync 2> airlines-sync.jsonl`.

Фильтр событий и подсчёт по видам:

```bash
go run ./cmd/cli airlines sync --dry-run 2> sync.jsonl
jq -c 'select(.event | startswith("airline_sync."))' sync.jsonl
jq -r 'select(.event | startswith("airline_sync.")) | .event' sync.jsonl | sort | uniq -c
```

Число событий совпадает со строками `anomaly …` итога (проверено на прогоне 2026-10-21).

Первые шесть — свойства данных Wikidata: держатся на этом уровне от прогона к прогону и меняются
медленно. Повод разобраться — **рост** любого счётчика больше чем на ~10% за месяц, а также
`merged`/`missing`/`merge_target_unknown` больше единиц за прогон (за месяц в источнике пропадают
единицы записей; десятки — признак массовой правки или усечённого ответа). Ошибка полноты
(`airline source response looks incomplete`) — не событие, а ошибка прогона: перезапустить позже.
