## Контекст

Api считал длительности и хронологию по «часам на циферблате», не зная таймзон, и молча отбрасывал
смещение, если его передать: время перелётов между поясами искажалось. Кроме того, в карточке были
только коды ICAO, а web нужно показывать город, название и код IATA. Оба расхождения мешают
подключить web к перелётам api.

**Инварианты:**

- **Время сегмента — местное.** `departure_at` — в аэропорту вылета, `arrival_at` — в аэропорту
  прилёта, формат `YYYY-MM-DDTHH:MM:SS`. Хранится только оно, миграции нет. Запись с `Z` или смещением
  отклоняется с `400`, в ответе суффикса нет. **BREAKING** для клиентов `flights`.
- **Момент вычисляется, а не хранится.** При каждой проверке и расчёте — `time.Date(…, loc)` по таймзоне
  города аэропорта на эту дату (`airport.Zones`: таймзона — знание об аэропорте, поэтому тип в его пакете, ревью api PR №38); зоны нет или она неизвестна — UTC.
- **Домен.** `Segment.DepartureAt`/`ArrivalAt` несут настенные часы в `time.UTC`; вычитать их напрямую
  нельзя. `flight.New` проверяет только правила без времени, хронология и пересадки —
  `flight.CheckChronology(f, zones)`, её вызывает `Manager` после загрузки аэропортов. Коды ошибок прежние.
- **Карточка.** `departure_airport`/`arrival_airport` — всегда объекты с текущими данными справочника;
  поля с кодами ICAO остаются. Загрузка — одним запросом (`helpers.FindSegmentAirports`), им же берутся
  зоны для длительностей.
- **Presentation.** `offerhttp.LocalDateTime` и `offerhttp.AirportResponse` — в родительском пакете ресурса:
  они общие для нескольких хендлеров (`STYLE.md` §3).

## Non-goals

- Хранение смещения или UTC-момента, выдача UTC-момента в ответе.
- Объекты аэропортов у пересадок и у перелёта целиком.
