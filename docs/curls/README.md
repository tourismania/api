# docs/curls — примеры запросов для ручного тестирования

Набор `curl`-сценариев для `/api/v1/*` и `/api/login`: не только happy path, но и
пограничные случаи (валидация, роли, владение по агентству, вариации `flights`
у offer). Каждый файл — самостоятельный bash-скрипт (можно запускать целиком)
и одновременно набор отдельных `curl`-команд, которые удобно копировать по
одной в Postman/Insomnia.

**Это не замена Swagger.** Swagger (`docs/swagger/`, генерируется `make swag`)
— машиночитаемый источник истины по контракту всех эндпоинтов и **обновляется
автоматически** при каждом изменении `@Param`/`@Success`/DTO в хендлере.
`docs/curls/` — это готовые бизнес-сценарии (в том числе комбинации полей,
которые в OpenAPI не выразить: "flights отсутствует — не трогаем",
"flights: [] — очищаем", "пересадка нулевой длительности — 400" и т.п.) и
обновляется **вручную**. См. раздел "Как поддерживать в актуальном состоянии"
ниже и оптимизацию через Swagger в конце этого файла.

## Быстрый старт

```bash
export BASE_URL=http://localhost:8080   # значение по умолчанию, можно не задавать

# 1. Получить агентство и агента с ролью (см. "Ограничение: роли" ниже)
# 2. Залогиниться
bash docs/curls/00-auth.sh
# скопировать token из ответа
export TOKEN=eyJhbGciOi...

# 3. Прогнать любой сценарий
bash docs/curls/03-offers-create.sh
```

Каждый скрипт печатает тело ответа и HTTP-статус (`--- HTTP <код> ---`) после
каждого запроса, чтобы было видно, что сценарий сработал так, как описан в
комментарии над ним.

## Файлы

| Файл | Что покрывает |
|------|----------------|
| `00-auth.sh` | `POST /api/login` — успех, неверный пароль |
| `01-users.sh` | `POST /api/v1/users`, `GET /api/v1/users/me` — успех, несуществующее/неактивное агентство, дубликат email |
| `02-airports.sh` | `GET /api/v1/airports` — успех, `search` короче 2 символов, пагинация |
| `03-offers-create.sh` | `POST /api/v1/offers` — без flights, с одним перелётом, с пересадкой (2 сегмента), невалидная хронология, разрыв маршрута, несуществующий `icao`, недостаточная роль (`403`) |
| `04-offers-update.sh` | `PATCH /api/v1/offers/{uuid}` — обновление title/status без `flights`, `flights` отсутствует (не трогаем), `flights: []` (очистка), замена `flights`, чужое агентство (`404`) |
| `05-offers-read.sh` | `GET /api/v1/offers`, `GET /api/v1/offers/{uuid}`, `GET /api/v1/public/offers/{uuid}` — список с фильтрами, чужое агентство (`404`), публичная ссылка на неопубликованный offer (`404`) |
| `06-offers-delete.sh` | `DELETE /api/v1/offers/{uuid}` — успех (`204`), повторное удаление (`404`) |

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `BASE_URL` | нет (default `http://localhost:8080`) | адрес поднятого сервера |
| `TOKEN` | да, для всех `/api/v1/*` кроме `GET /public/offers/{uuid}` | JWT, полученный из `00-auth.sh` |
| `OFFER_UUID` | да, для `04-offers-update.sh`/`05-offers-read.sh`/`06-offers-delete.sh` | `uuid` offer'а, полученный из ответа `03-offers-create.sh` |
| `AGENCY_ID` | нет (default `1`) | `agency_id` для `POST /api/v1/users` |

## Ограничение: роли

Ни HTTP, ни CLI (`user create`) сейчас не позволяют выставить `ROLE_AGENT`/
`ROLE_SUPER_ADMIN` — у только что зарегистрированного пользователя список
ролей пуст (эквивалентно `ROLE_USER`). Это удобно для сценария `403` в
`03-offers-create.sh` (просто используйте токен свежесозданного пользователя
как есть), но для happy-path сценариев (создание/изменение/удаление offer)
нужен пользователь с ролью `ROLE_AGENT` или `ROLE_SUPER_ADMIN`, выставленной
сейчас **только напрямую в БД**:

```sql
UPDATE users SET roles = '{ROLE_AGENT}' WHERE email = 'ada@example.com';
```

(Нет отдельной команды на назначение роли — возможный кандидат в
`docs/tech_debt/tasks.md`, если команда сочтёт это нужным.)

## Импорт в Postman

1. **Предпочтительно — сразу весь контракт:** `Import → File → docs/swagger/swagger.json`
   (см. "Оптимизация тестирования" ниже) — получаете структурированную
   коллекцию по всем эндпоинтам, которая пересобирается вместе с кодом.
2. **Точечно, конкретный сценарий отсюда:** откройте нужный `.sh`-файл,
   скопируйте одну `curl`-команду (без предшествующего `#`-комментария) и
   вставьте через `Import → Raw text` (Postman сам распознаёт `curl`).
   Значения `${BASE_URL}`/`${TOKEN}`/`${OFFER_UUID}` останутся в запросе как
   текст — замените их вручную или добавьте те же имена как collection
   variables без `$`/`{}` (`BASE_URL`, `TOKEN`, `OFFER_UUID`) и включите
   Postman-синтаксис `{{BASE_URL}}` перед импортом.

## Импорт в Insomnia

Insomnia умеет то же самое: `Import → From File`. Спокойно принимает как
`docs/swagger/swagger.json` (нативная поддержка OpenAPI/Swagger 2.0), так и
отдельный `curl`, вставленный через `Import → From Clipboard`.

## Как поддерживать в актуальном состоянии

При изменении контракта существующего эндпоинта (новое/переименованное
поле, новый код ошибки, новая комбинация допустимых значений) или при
добавлении нового эндпоинта — обновить/добавить соответствующий сценарий в
профильном файле этой папки. Это ручной шаг (см. таблицу "Documentation
Maintenance" в `CLAUDE.md`), в отличие от `docs/swagger`, который
пересобирается автоматически.

## Оптимизация тестирования: почему не хранить готовую Postman/Insomnia коллекцию в git

Явно сгенерированный JSON коллекции (Postman Collection v2.1 или
Insomnia export) — ещё один артефакт, который придётся вручную
пересобирать и коммитить при каждом изменении хендлера, то есть то же самое
дублирование источника истины, из-за которого мы не коммитим `docs/swagger/`
(см. `CLAUDE.md`: "генерируется автоматически", "не редактируется
вручную"). Вместо этого:

- **Источник истины — Swagger-аннотации в хендлерах** (`@Param`, `@Success`,
  `@Failure`, DTO-структуры). `make swag` уже обязателен при изменении
  хендлера (см. `CLAUDE.md` → Documentation Maintenance).
- **И Postman, и Insomnia импортируют `docs/swagger/swagger.json` напрямую**
  (`File → Import`, формат OpenAPI/Swagger 2.0 поддерживается нативно, без
  конвертации) — это даёт актуальную коллекцию по всем эндпоинтам без
  дополнительного шага/инструмента и без риска рассинхронизации, потому что
  она собирается из того же кода, что и сам эндпоинт.
- **`docs/curls/` остаётся дополнением**, а не заменой: здесь — конкретные,
  документированные бизнес-сценарии (комбинации полей, граничные случаи),
  которые из голого OpenAPI-контракта не восстановить, и которые стоит
  явно проговаривать в review при изменении соответствующего эндпоинта.

Итог рабочего процесса при доработке эндпоинта:

1. Меняете хендлер/DTO + Swagger-аннотации (как и раньше).
2. `make swag` — `docs/swagger/swagger.json` актуализируется автоматически.
3. Re-import `docs/swagger/swagger.json` в Postman/Insomnia (пересоздаёт
   коллекцию с нуля за секунды — существующая история запросов/переменные
   окружения не трогаются).
4. Если менялся бизнес-сценарий (не просто форма ответа) — обновить
   соответствующий файл в `docs/curls/` вручную.
